\CourseSection{Functional Description}\label{sec:functional-description}
\CourseSubsection{System overview}

The pipeline of Figure~\ref{fig:system} decomposes into five functions, each allocated to one software element. F1 ingests the GitSkills tables, which are distributed as one SQLite database with a Parquet copy of each table: \texttt{artifacts}, \texttt{artifact\_siblings}, \texttt{repos}, and \texttt{mining\_runs}. F2, one pre-processing step shared by every metric, keeps one row per distinct skill (\textit{dedup\_primary} = 1, a \textit{filename} of SKILL.md, valid front matter, not a symlink, and a non-empty body) and splits its \textit{content} into front matter, prose, and code. F3 calculates each metric in a separate module (F3.1 size, F3.2 churn, F3.3 age, F3.4 clone coverage, F3.5 readability), F4 joins the results into one metrics file, and F5 produces statistics and plots. Appendix~\ref{app:interfaces} gives the interfaces (I1 to I7), tools, and design decisions.
We query a fixed snapshot in batches with DuckDB~\cite{raasveldt2019duckdb}, because live GitHub mining changes between runs and loading the 44~GB database into memory exceeds the limit in PF-02. Each stage writes Parquet, so a failed stage restarts without repeating earlier ones. The only input from outside the dataset is a small sample of cloned GitHub repositories used for token churn.

\needspace{5\baselineskip}
\noindent\textbf{Size Calculation Module.}

The Size module counts the tokens in each of a skill's three tiers: the description, the body (prose and code), and the bundle, which only counts the text files whose content GitSkills stored.
Skills with \textit{composition\_truncated} = 1 are flagged, since their bundle listing is incomplete.
Lines and words are also counted for the body, along with lines and tokens for each bundled script, so skills can be compared directly with ordinary code.
The output is one row of size columns per \textit{file\_sha}, plus a separate file for the bundled scripts.

\medskip

\needspace{5\baselineskip}
\noindent\textbf{Churn Calculation Module.}

The Churn module splits into three calculations.
\textit{Activity churn} uses the commit fields of every skill with history (\textit{history\_fetched} = 1) to find how many times it was edited (\textit{commit\_count} minus 1), its edits per month, how long it was actively edited, and how long it has sat untouched up to the snapshot date (\textit{finished\_at} in \textit{mining\_runs}).
It also flags first or last commits that were AI co-authored or made by a bot, and whether the author changed between them.
\textit{Token churn} follows a sample of edited skills, stratified by \textit{location\_class}, through their cloned histories, renames included, and counts the tokens added and removed between each pair of consecutive versions.
\textit{Cross-copy churn} orders each near-clone family by \textit{first\_commit\_at}, or by the repository's \textit{created\_at} when a skill has no history, then compares each skill with its most similar earlier member and counts the tokens added and removed.
Activity and token churn go into the churn columns, while each link from a parent to its child goes into a separate lineage file, along with its similarity, its token counts, and which date was used to decide its direction.

\medskip

\noindent\textbf{Age Calculation Module.}

\begin{figure}[htbp]
\centering
\includegraphics[width=\linewidth]{figures/age-function.pdf}
\caption{Functional decomposition of the Age calculation module.}
\label{fig:age-function}
\end{figure}

The age module calculates how long the SKILL.md file has been inside the repository. It uses the \texttt{first\_commit\_at} timestamp and a fixed dataset collection date to calculate the age of the skill. The purpose of the fixed dataset collection date is to assure consistency across the dataset. The module will output the calculated age value (displayed in days). This value will be passed to the output stage for analysis and potential visualization. Records with missing or invalid values in the texttt{first\_commit\_at} field will not be imputed but will be flagged instead. The use of the first commit date has been selected to determine age over the latest commit date as the team looks to measure how long the skill has existed rather than how long since the skills final edit.

\medskip

\noindent\textbf{Clone Coverage Calculation Module.}

\begin{figure}[htbp]
\centering
\includegraphics[width=\linewidth]{figures/cc-function.pdf}
\caption{Functional decomposition of the Clone Coverage calculation module.}
\label{fig:cc-function}
\end{figure}

The Clone Coverage module measures how frequently identical or substantially similar AI agent skills appear within the GitSkills dataset, following the process shown in Figure~\ref{fig:cc-function}. Exact clones are identified by grouping skill occurrences with matching \texttt{file\_sha} values. Groups containing multiple occurrences are classified as exact clone groups, and exact clone coverage is calculated as the percentage of eligible skill occurrences belonging to these groups, including the first occurrence.

Near-clones will be identified using the actual skill text stored in the \texttt{content} field, regardless of repository or filename. The \texttt{dedup\_primary} field will be used to select representatives of exact-content groups, while \texttt{content\_fetched} and \texttt{content\_sha\_ok} will verify text availability and integrity. Skill text will be divided into overlapping three-token sequences (shingles), and MinHash signatures with locality-sensitive hashing (LSH) will identify potentially similar pairs. These pairs will then be evaluated using Jaccard similarity, calculated as the number of shared shingles divided by the total number of unique shingles across both skills.

Pairs with different file hashes and Jaccard similarity exceeding a selected threshold will be classified as near-clones. Rather than choosing a fixed threshold beforehand, several thresholds will be evaluated against manually reviewed skill pairs to determine which best distinguishes near-clones from unrelated skills. Qualifying relationships will be combined into connected clone groups, allowing multiple related skills to be grouped together even when not every pair exceeds the threshold. These groups will be mapped back to the original skill occurrences, and expanded clone coverage will be calculated as the percentage of eligible occurrences belonging to groups containing multiple skills. Exact and expanded clone coverage will be reported separately, with missing or invalid data handled separately.

\noindent\textbf{Readability Calculation Module.}

Figure~\ref{fig:readability-functional} decomposes readability from ingestion to outputs, and Figure~\ref{fig:readability-logical} allocates each function to a logical element~\cite[Sec.~4.3]{nasa2016handbook}. Pre-processing (F2) supplies the description, prose, and code of each distinct skill, which we score separately so that one part cannot hide another.
Readability formulas count words per sentence, so F2.2 parses the Markdown rather than scoring raw text. It joins hard-wrapped lines, which occur in 37\% of skills in our pilot on the 13,000-skill sample; removes inline code, which formulas misread as short words~\cite{chatlatanagulchai2026agent}; and emits each heading, list item, and table row as one sentence. Scoring raw text would instead raise the median grade from 9.1 to 12.2.
English prose receives the Flesch--Kincaid grade~\cite{kincaid1975}, which needs only sentence length and syllables per word, so it is repeatable, requires no training data, and expresses difficulty as a school grade. Coleman--Liau~\cite{coleman1975} is the cross-check because it counts letters instead of syllables, which independently checks syllable counting in technical text; the two agreed closely in the pilot ($\rho = 0.90$). We rejected Gunning Fog~\cite{gunning1952} and SMOG~\cite{mclaughlin1969smog}, which also rely on syllables and track Flesch--Kincaid closely, and Dale--Chall~\cite{chall1995}, which counts technical terms as unfamiliar. The closest prior work scored agent context files with Flesch Reading Ease and found only a weak link to human judgement ($\rho = 0.19$)~\cite{chatlatanagulchai2026agent}, so we report grades as reading-level estimates, not as measures of quality.
Code blocks and bundled scripts, read as text and never run, are cut into equal 10-line windows, within the 4-to-11-line snippets behind Posnett's model~\cite{posnett2011simpler}, and scored with its linear output, because its sigmoid output falls below 0.01 for 91\% of pilot skills. Its authors caution against applying it blindly, and it tracked developers weakly on AI-generated Java (MCC $= -0.036$)~\cite{sergeyuk2024reassessing}, so this score is also an estimate. Prose and code use different scales, so we compare with source code only through the code model, using the scripts bundled with about 11\% of skills. F5 reports medians, interquartile ranges, and the effect size Cliff's $\delta$~\cite{cliff1993dominance}, with distribution plots.

\CourseSubsection{Risks and safety hazards}
The pipeline has no physical hazard. Three risks remain, each limited by a requirement.
\textbf{Untrusted code.} A bundled script may compromise a team machine if run: GitSkills holds 7.26 million bundled files, and skills are copied without formal review~\cite{msr2027MiningChallenge}. SYS-6 limits the pipeline to reading them as text.
\textbf{Privacy.} Repository names remain identifiable although commit authors are coded. The data fits the TCPS~2 exemptions for public and anonymous information~\cite[Arts.~2.2, 2.4]{tcps2022}, and we report aggregates only; we will confirm with the supervisor that no ethics review is needed.
\textbf{Licensing.} Skill text stays under each repository's license~\cite{gitskills2027}, so SYS-5 limits the replication package to derived metrics.
