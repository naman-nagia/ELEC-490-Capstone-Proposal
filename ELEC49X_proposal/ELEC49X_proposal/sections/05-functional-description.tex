\CourseSection{Functional Description}\label{sec:functional-description}
\CourseSubsection{System overview}

The pipeline of Figure~\ref{fig:system} decomposes into five functions, each allocated to one software element~\cite[Sec.~4.3]{nasa2016handbook}: F1 ingests the GitSkills tables, F2 prepares records and filters out files that are not genuine skills, F3 calculates each metric in a separate module (F3.1 size, F3.2 churn, F3.3 age, F3.4 clone coverage, F3.5 readability), F4 joins the results into one metrics file, and F5 produces statistics and plots. Appendix~\ref{app:interfaces} gives the interfaces (I1 to I7), tools, and design decisions.
We query a fixed snapshot in batches with DuckDB~\cite{raasveldt2019duckdb}, because live GitHub mining changes between runs and loading the 44~GB database into memory exceeds the limit in PF-02. Each stage writes Parquet, so a failed stage restarts without repeating earlier ones. The only input from outside the dataset is a small sample of cloned GitHub repositories used to validate churn.

\medskip

\noindent\textbf{Age Calculation Module.}

The age module calculates how long the SKILL.md file has been inside the repository. It uses the \texttt{first\_commit\_at} timestamp and a fixed dataset collection date to calculate the age of the skill. The purpose of the fixed dataset collection date is to assure consistency across the dataset. The module will output the calculated age value (displayed in days). This value will be passed to the output stage for analysis and potential visualization. Records with missing or invalid values in the texttt{first\_commit\_at} field will not be imputed but will be flagged instead. The use of the first commit date has been selected to determine age over the latest commit date as the team looks to measure how long the skill has existed rather than how long since the skills final edit.

\medskip

\noindent\textbf{Clone Coverage Calculation Module.}

The Clone Coverage module measures how frequently identical or substantially similar AI agent skills appear within the GitSkills dataset. Exact clones are identified by grouping skill occurrences with matching \texttt{file\_sha} values. Groups containing multiple occurrences are classified as exact clone groups, and exact clone coverage is calculated as the percentage of eligible skill occurrences belonging to these groups, including the first occurrence.

Near-clones will be identified using the actual skill text stored in the \texttt{content} field, regardless of repository or filename. The \texttt{dedup\_primary} field will be used to select representatives of exact-content groups, while \texttt{content\_fetched} and \texttt{content\_sha\_ok} will verify text availability and integrity. Skill text will be divided into overlapping three-token sequences (shingles), and MinHash signatures with locality-sensitive hashing (LSH) will identify potentially similar pairs. These pairs will then be evaluated using Jaccard similarity, calculated as the number of shared shingles divided by the total number of unique shingles across both skills.

Pairs with different file hashes and Jaccard similarity of at least 80\% will be linked as near-clones. This threshold follows published text deduplication research and requires substantial textual overlap while allowing minor modifications. Qualifying relationships will be combined into connected clone groups, allowing multiple related skills to be grouped together even when not every pair exceeds the threshold. These groups will be mapped back to the original skill occurrences, and expanded clone coverage will be calculated as the percentage of eligible occurrences belonging to groups containing multiple skills. Exact and expanded clone coverage will be reported separately, with missing or invalid data handled separately.

\medskip

\noindent\textbf{Readability Calculation Module.}

Figure~\ref{fig:readability-functional} decomposes readability from ingestion to outputs, and Figure~\ref{fig:readability-logical} allocates each function to a software element.
F1.1 takes one representative row per distinct content, since identical files score identically, and F2.1 keeps verified files named exactly \texttt{SKILL.md} with valid front matter. F3.5.1 and F3.5.2 split each skill into description, prose, and code, because one whole-file score would mix prose with code.
Readability formulas count words per sentence, so F3.5.3 emits each heading, list item, and table row as its own sentence; otherwise a bullet list counts as one long sentence and the median grade rises from 8.6 to 12.2. English prose receives the Flesch--Kincaid grade~\cite{kincaid1975}, which needs only sentence length and syllables per word, so it is free, repeatable, requires no training data, and expresses difficulty as a school grade. Coleman--Liau~\cite{coleman1975} is the cross-check because it counts letters instead of syllables: it is an independent check on syllable counting in technical text, and the two agreed closely in the pilot ($\rho = 0.92$). Both were calibrated on general text rather than agent instructions, so we report their grades as reading-level estimates, not as measures of quality.
Code blocks and bundled scripts, read as text and never run, are cut into equal 10-line windows and scored with the linear output of Posnett's model~\cite{posnett2011simpler}, because its sigmoid output falls below 0.01 for 90\% of pilot skills.
Prose and code use different scales, so we compare with source code only through the code model, using the scripts bundled with about 11\% of skills. F5 outputs medians, interquartile ranges, Cliff's $\delta$~\cite{cliff1993dominance}, and distribution plots. Appendix~\ref{app:interfaces} records the alternatives we rejected.

\CourseSubsection{Risks and safety hazards}
We use the ISO~31000 sense of risk, the effect of uncertainty on objectives~\cite{iso31000}, and size each risk from measured exposure. The pipeline is desk-based software with no physical hazard.
\textbf{Untrusted code.} GitSkills holds 7.26 million bundled files from unreviewed repositories, and running one could compromise a team machine, so the pipeline reads them only as text (SYS-6, T10).
\textbf{Privacy.} The data is public and commit authors are coded, which fits the TCPS~2 exemptions for public and anonymous information~\cite[Arts.~2.2, 2.4]{tcps2022}. Repository names remain identifiable, so we report aggregates only; we will confirm with the supervisor that no ethics review is needed.
\textbf{Licensing.} Skill text stays under each repository's license~\cite{gitskills2027}, so we release derived metrics only (SYS-5).
\textbf{Scale.} The 44~GB database is 2.75 times the 16~GB memory limit, which batched reads manage.
